# เอกสารตัวอย่างสำหรับผู้เข้าอบรม (Sample Knowledge Files)

โฟลเดอร์นี้เป็นไฟล์ **Knowledge Source ตัวอย่าง** ให้ผู้เข้าอบรมแต่ละแผนก Upload ขึ้น SharePoint ส่วนตัว (หรือแนบไฟล์ตรง) แล้วใช้เป็น Knowledge ใน Lab 2 (Copilot Studio + Knowledge) ได้ทันที — ไฟล์กลุ่ม Word (.docx) ทุกไฟล์ถูกสร้างเป็นไฟล์ .docx จริงไว้ให้แล้ว ไม่ต้อง Copy/วางเอง

ไฟล์ส่วนใหญ่ใช้บริษัทสมมติเดียวกันคือ **"บริษัท XYZ อินดัสตรี จำกัด"** เพื่อให้เนื้อหาสอดคล้องกันและดูสมจริงเวลาถาม-ตอบ (ยกเว้นไฟล์ของแผนก IT 2 ไฟล์ที่เป็นเอกสารจริงของบริษัท — ดูหมายเหตุท้ายไฟล์) แยกโฟลเดอร์ย่อยตามกลุ่มงานให้ครบ 6 โฟลเดอร์ ครอบคลุมทั้ง 7 แผนกที่เข้าอบรม (Engineer และ Warehouse ใช้โฟลเดอร์ `Safety/` ร่วมกัน เพราะเนื้อหาเชื่อมโยงกันเรื่องความปลอดภัยในโรงงาน) — ผู้เข้าอบรมเปิดแค่โฟลเดอร์แผนกตัวเองได้เลย ไม่ต้องหาไฟล์ปนกับแผนกอื่น

ไฟล์ `.md` แต่ละไฟล์เก็บไว้เป็นต้นทางให้แก้ไขเนื้อหาได้ง่าย (เช่น เปลี่ยนชื่อบริษัท/ตัวเลข) — ถ้าแก้ไข ให้รันสร้าง `.docx` ใหม่อีกครั้งด้วยสคริปต์แปลงไฟล์ (ดูหัวข้อถัดไป) หรือ Copy เนื้อหาไปวางใน Word เองตามขั้นตอนแบบเดิม

## วิธีแปลง/สร้างไฟล์ใหม่ (ถ้าแก้ไขเนื้อหา)

1. **Word (.docx)**: แก้เนื้อหาในไฟล์ `.md` ที่ต้องการ แล้วรันสคริปต์ Node ที่ใช้ Library [`docx`](https://www.npmjs.com/package/docx) แปลง Markdown (`#`/`##` = Heading, ตาราง `|...|` = Table, `**text**` = ตัวหนา) เป็นไฟล์ `.docx` จริงโดยอัตโนมัติ (ไม่ต้องเปิด Word เอง) — หรือจะ Copy เนื้อหาไปวางใน Word เองแล้วจัด Heading/ตารางเองก็ได้เช่นกัน
2. **PDF**: เปิด `Warehouse/factory_safety_policy.md` (หรือไฟล์ `.docx` ที่แปลงแล้ว) → File → Save As / Print → PDF
3. **Excel**: เปิด `Sales_Engineer/sales_data_raw.csv` ด้วย Excel โดยตรง (ไฟล์มี UTF-8 BOM แล้ว ภาษาไทยจะไม่เพี้ยน) → Save As เป็น `sales_data_raw.xlsx`

## โครงสร้างข้อมูล Sales Data

คอลัมน์ในไฟล์: `สาขา, หมวดสินค้า, ปี (พ.ศ.), เดือน, ยอดขาย (บาท), จำนวนรายการ`

- **สาขา**: กรุงเทพ, ชลบุรี, ขอนแก่น (3 สาขา)
- **หมวดสินค้า** (9 หมวด แบ่งเป็นสินค้าหลัก 4 หมวด + อะไหล่แยกย่อย 5 รายการ):
  - รถ Forklift ใหม่ (หน่วย: คัน)
  - รถ Forklift มือสอง (หน่วย: คัน)
  - อุปกรณ์เสริม (Attachment) (หน่วย: ชิ้น)
  - บริการให้เช่ารถ Forklift (หน่วย: สัญญา)
  - บริการซ่อมบำรุง (หน่วย: ครั้ง)
  - ยาง (หน่วย: เส้น)
  - แบตเตอรี่ (หน่วย: ลูก)
  - ใบมีดยก (Fork) (หน่วย: คู่)
  - น้ำมันไฮดรอลิก (หน่วย: ถัง)
- **ช่วงเวลา**: ปี 2568-2569 (12 เดือน/ปี)
- รวม 3 สาขา × 2 ปี × 12 เดือน × 9 หมวดสินค้า = **648 แถว** ของข้อมูลดิบ มีแนวโน้มฤดูกาล (ยอดสูงช่วง พ.ย.-เม.ย.) และเติบโตปีต่อปีแตกต่างกันตามสาขา

## จุดประสงค์การออกแบบ — ทำไมข้อมูลถึงเป็นแบบนี้

- **Work Permit / Safety Policy** — มีข้อมูลเฉพาะเจาะจง (ตัวเลข, ขั้นตอน, เงื่อนไข, กรณีศึกษา) ที่ตรวจคำตอบถูก/ผิดได้ง่าย เหมาะสาธิตความแม่นยำของ RAG และการอ้างอิงแหล่งที่มา (Referenced sources) เนื้อหาที่ยาวและมีหลายหัวข้อยังช่วยสาธิตพฤติกรรม Chunking ของ Copilot Studio ได้ดี — ลองถามคำถามที่คำตอบอยู่คนละหัวข้อกัน แล้วดูว่า Agent ยังหาเจอหรือไม่
- **Sales Data** — ตั้งใจให้เป็น **Raw Data ล้วนๆ ไม่มี Sheet สรุปยอดรวม** เพื่อสาธิตข้อจำกัดจริงของ RAG: Copilot Studio ดึงข้อมูลเป็น "ชิ้นข้อความที่เกี่ยวข้อง" ไม่ได้รันสูตรคำนวณ SUM/AVERAGE จากตารางทั้งหมด ดังนั้น
  - คำถามที่หา **ค่าเจาะจงจุดเดียว** (สาขาเดียว/หมวดเดียว/เดือนเดียว) → บอทมักตอบถูก (เพราะเป็นการ "หา" ไม่ใช่ "คำนวณ")
  - คำถามที่ต้อง **รวมยอด/เฉลี่ยข้ามหลายแถว** (ข้ามสาขา ข้ามหมวดสินค้า หรือข้ามเดือน) → บอทมักตอบผิดแบบเนียนๆ (เห็นข้อมูลไม่ครบทุกแถว)
  - การมีทั้งมิติสาขาและหมวดสินค้าพร้อมกันยังช่วยให้เห็นชัดขึ้นว่าคำถามยิ่งซับซ้อน (ต้องรวมหลายมิติ) ยิ่งมีโอกาสตอบผิดสูงขึ้น
  - นี่คือจุดสอนที่ดีเรื่องข้อจำกัดของ RAG และโยงต่อไปยัง Lab 5 (Evaluation) ได้พอดี
  - **`sales_data_summary_report.docx`** คือไฟล์เสริมที่เตรียมไว้ใช้สาธิตขั้น "Improve" ของ RAG Improvement Loop (Lab 5) โดยเฉพาะ — หลังให้ผู้เรียนเห็นว่าคำถามรวมยอด/เฉลี่ยข้ามแถวตอบผิดจาก Raw Data อย่างเดียว ให้ลองเพิ่มไฟล์นี้เป็น Knowledge Source ที่ 2 แล้วถามคำถามเดิมซ้ำอีกครั้ง จะเห็น Pass Rate ดีขึ้นทันทีเพราะ Agent มีตัวเลขสรุปสำเร็จรูปให้ดึงตรงๆ แทนที่จะต้องคำนวณเอง — **อย่าเพิ่งแนบไฟล์นี้ตั้งแต่ Lab 2** เก็บไว้ใช้ตอน Lab 5 เพื่อให้เห็น Before/After ชัดเจน
